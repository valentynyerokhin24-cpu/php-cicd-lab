# Архітектура інтернет-магазину комп'ютерної техніки

## 1. Призначення та межі системи

Система призначена для продажу комп'ютерної техніки та комплектуючих через вебсайт. Відвідувачі переглядають каталог, шукають товари й реєструються. Зареєстровані покупці керують кошиком, оформлюють замовлення, оплачують його та відстежують доставку. Адміністратор підтримує каталог і замовлення, переглядає звіти. Оплата й доставка інтегруються із зовнішніми сервісами.

Цей документ описує проєктну модель навчальної системи. Поточний репозиторій `php-cicd-lab` містить навчальний приклад PHP CI/CD, а не реалізацію магазину; наведені нижче класи та дані є архітектурним проєктом, а не твердженням про вже реалізований функціонал.

### Основні функції

1. Перегляд каталогу, фільтрація та пошук за назвою, категорією, виробником і ціною.
2. Реєстрація, автентифікація та редагування профілю покупця.
3. Керування кошиком і перевірка доступності товарів.
4. Оформлення замовлення з адресою та способом доставки.
5. Оплата замовлення через зовнішній платіжний сервіс.
6. Перегляд історії замовлень, статусу оплати й доставки.
7. Керування товарами, категоріями, замовленнями та відгуками адміністратором.
8. Формування звітів про продажі та залишки.

### Актори

| Актор | Роль |
|---|---|
| Гість (`Guest`) | Переглядає та шукає товари, може зареєструватися. |
| Покупець (`Customer`) | Зареєстрований користувач, який успадковує можливості гостя та оформлює покупки. |
| Адміністратор (`Administrator`) | Керує каталогом і замовленнями та формує звіти. |
| Платіжний сервіс (`Payment Gateway`) | Авторизує оплату, повертає кошти й надає стан транзакції. |
| Служба доставки (`Courier Service`) | Приймає відправлення та передає інформацію про його переміщення. |

## 2. Архітектура MVC

Система поділяється на три логічні шари MVC:

- **Model:** `User`, `Customer`, `Administrator`, `Address`, `Category`, `Product`, `Cart`, `CartItem`, `Order`, `OrderItem`, `Payment`, `Shipment`, `Review`. Моделі відповідають за стан предметної області, зв'язки та бізнес-правила. У реалізації на Laravel вони можуть бути Eloquent-моделями.
- **View:** сторінки каталогу й товару, форми автентифікації та оформлення замовлення, кабінет покупця, панель адміністратора. Представлення формують HTML для браузера; відповіді зовнішнього API можуть бути JSON.
- **Controller:** `CatalogController`, `CartController`, `CheckoutController`, `OrderController`. Контролери приймають HTTP-запити, перевіряють введення й повноваження, викликають бізнес-сервіси та повертають представлення або перенаправлення. Доступ до платіжного провайдера й доставки має бути ізольований за сервісними адаптерами.

Контролери не повинні самостійно дублювати правила ціноутворення, резервування запасів чи переходів статусів. Ці правила належать моделям або сервісному шару. Для Laravel слід застосувати валідацію запитів, middleware авторизації, CSRF-захист і зберігання паролів лише у вигляді стійкого хешу.

## 3. Основний сценарій роботи

1. Гість переглядає каталог, відкриває товар і додає потрібну кількість до кошика.
2. Перед оформленням система перевіряє наявність товарів і фіксує ціну позицій у кошику.
3. Покупець входить або реєструється, вибирає адресу й спосіб доставки.
4. Система створює замовлення та його незмінні на момент покупки позиції.
5. Платіжний сервіс авторизує оплату. У разі успіху замовлення переходить у стан «оплачено/в обробці».
6. Адміністратор передає замовлення на комплектування; служба доставки надає номер відстеження й оновлює статус.
7. Покупець переглядає історію та може залишити відгук після завершення замовлення.

## 4. Логічні сутності та таблиці даних

| Сутність / таблиця | Ключові дані | Призначення та зв'язки |
|---|---|---|
| `users` | `id`, `full_name`, `email`, `password_hash`, `phone`, `status` | Спільні облікові дані покупців та адміністраторів; email унікальний. |
| `addresses` | `id`, `user_id`, `recipient`, `city`, `street`, `postal_code` | Адреси користувача; один користувач може мати декілька адрес. |
| `categories` | `id`, `name`, `slug`, `description`, `is_active` | Категорії каталогу; категорія має багато товарів. |
| `products` | `id`, `category_id`, `sku`, `name`, `price`, `stock_quantity` | Каталог товарів; SKU унікальний, ціна невід'ємна. |
| `carts` | `id`, `customer_id`, `status`, `expires_at`, `created_at` | Активний кошик покупця. |
| `cart_items` | `id`, `cart_id`, `product_id`, `quantity`, `unit_price_snapshot` | Позиції кошика; унікальна пара кошик-товар. |
| `orders` | `id`, `customer_id`, `number`, `status`, `subtotal`, `total` | Замовлення покупця з унікальним номером і контрольованими переходами статусу. |
| `order_items` | `id`, `order_id`, `product_id`, `sku_snapshot`, `quantity`, `unit_price_snapshot` | Знімок придбаних позицій; зберігає ціну та назву на момент покупки. |
| `payments` | `id`, `order_id`, `provider`, `amount`, `status`, `transaction_reference` | Транзакції; зовнішній ідентифікатор унікальний, де це підтримує провайдер. |
| `shipments` | `id`, `order_id`, `carrier`, `tracking_number`, `status`, `shipped_at` | Відправлення, пов'язане із замовленням. |
| `reviews` | `id`, `customer_id`, `product_id`, `rating`, `comment`, `status` | Відгук покупця на товар; рейтинг від 1 до 5. |

Для фінансових сум використовується десятковий тип з фіксованою точністю, а не двійковий `float`. Створення замовлення та резервування запасу мають виконуватися транзакційно. Обробка повторних callback-запитів платіжного провайдера має бути ідемпотентною.

## 5. Вихідні дані системи

1. **HTML-сторінки:** каталог, картка товару, кошик, оформлення, профіль, історія замовлень і панель адміністратора.
2. **Електронні повідомлення:** підтвердження реєстрації, замовлення, оплати, відправлення та зміни статусу.
3. **Документи для покупця:** підтвердження замовлення та рахунок/квитанція у PDF.
4. **Дані інтеграцій:** JSON-відповіді платіжному провайдеру й службі доставки через захищені API.
5. **Звіти адміністратора:** підсумки продажів і залишків у вебподанні та експорті CSV/PDF.

## 6. Вимоги та бізнес-правила

- Гість може переглядати товари, але для оформлення замовлення потрібен автентифікований покупець.
- Кількість у кошику має бути цілим числом більше нуля та не перевищувати доступний запас.
- Під час оформлення ціна й опис позиції копіюються до `order_items`; наступна зміна каталогу не змінює вже створене замовлення.
- Замовлення не позначається оплаченим лише на підставі відповіді браузера; підтвердження приймається від перевіреного сервісного callback/API.
- Повернення коштів можливе лише для оплаченого замовлення та зберігається окремою транзакцією.
- Відгук може залишити лише покупець, який придбав відповідний товар; публікація може вимагати модерації.
- Адміністративні функції доступні лише авторизованим користувачам із відповідними повноваженнями.
- Зберігаються мінімально необхідні персональні дані; секрети інтеграцій не потрапляють у вихідний код чи журнали.
